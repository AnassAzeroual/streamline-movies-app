# Streamline — Source-Only Application Audit

**Report date:** 13 November 2026  
**Application:** Streamline (com.streamline.app)  
**Source revision audited:** current working tree at C:/Users/devtips/Documents/Streamline  
**Platform:** Android, minSdk 26, targetSdk 37, Kotlin/Compose, Media3 1.11.1, libtorrent4j 2.1.0-39

## Scope and method

This audit is based on the executable source code only. Code comments, README/Markdown material, prior conversation, and product claims were not treated as evidence. Every finding below is tied to a source location and the data/control flow visible there.

Reviewed areas:

- 59 Kotlin source files, approximately 11,619 lines under app/src/main/java.
- The catalog, domain models, eight index providers, player, torrent engine, DataSource, download manager, persistence, settings, manifest, FileProvider and network configuration.
- The complete unit-test tree: 19 files and 55 tests.
- Build configuration and the release artifact configuration.

Verification performed:

- :app:testDebugUnitTest: 55 tests, 0 failures.
- :app:assembleRelease: successful.
- No instrumentation tests are present under app/src/androidTest.
- No live endpoint, real torrent swarm, or long-running device test is part of this source audit.

The app is not a simple video player. It is an index aggregator, a live BitTorrent client, a sequential Media3 DataSource, a complete-file download queue, and a public-storage/export layer. Most of the highest-risk behavior is in the boundaries between those parts.

## 1. Executive verdict

The app has a coherent high-level split:

- Catalog providers return metadata and magnet links.
- A one-shot PlaybackRequest carries a selected release to the player.
- TorrentStreamEngine resolves metadata and exposes a TorrentPlayback.
- PlayerScreen feeds that playback into Media3 through TorrentDataSource.
- TorrentDownloadManager is a separate, app-scoped complete-file downloader.

The implementation is functional on the happy path, and several hard problems are addressed correctly: HTTPS-only archive traffic, bounded torrent metadata downloads, canonical-path validation for streamed files, direct/cache metadata validation, piece-alert wakeups, and a non-exported FileProvider.

The important weaknesses are not cosmetic:

1. The complete-download lifecycle is race-prone and can lose, resurrect, or orphan queue entries.
2. Many download operations are not tied to an Android foreground component, so process death ends them.
3. Multi-file torrents expose a directory where the export path assumes a file.
4. API 26–28 storage flow is effectively dead: the UI offers an action that cannot succeed.
5. The streaming engine keeps downloading after playback failure and does not cancel blocked DataSource reads.
6. The first-frame UI has no watchdog; missing container data can leave a permanent preparing screen.
7. Catalog aggregation hides provider failures and can permanently stall pagination.
8. Untrusted response bodies and torrent names are handled without sufficient bounds/containment.
9. The all-files storage model is extremely broad for an app that also processes untrusted torrent metadata.

## 3. Catalog and search subsystem

### 3.1 Source matrix

| Source | Transport | Paging | Detail fetch | Direct torrent URL | Main limit |
|---|---|---|---|---|---|
| YTS | HTTPS JSON API | 24 per page, page <= 200 | no | yes, torrents[].url | one preferred host cached for session |
| 1337x | HTTPS HTML scrape | 20 rows reported, only 10 loaded | yes, 4 concurrent | yes | Cloudflare, 5-host loop, empty parse short-circuit |
| TPB | HTTPS apibay JSON | no | no | no | only page 1; category 2xx filter |
| Torrents-CSV | HTTPS JSON | no | no | no | query required; 40 results |
| Knaben | HTTPS HTML scrape | page path | no | no | hideXXX hardcoded; positional stats |
| Nyaa | HTTPS RSS | p parameter, page < 20 | no | .torrent URL | hasMore heuristic based on 30 items |
| BTDigg | HTTPS HTML scrape | no | no | no | 30 results, no seeds/peers |
| Kickass | HTTPS HTML scrape | no | yes, 4 concurrent | yes | single host, 8 results |

The aggregate source ALL is implemented in DefaultMagnetCatalogRepository.kt:22-108:

- ALL with a blank query calls browseAllLatest.
- ALL with a query calls browseAll.
- Latest queries only sources with supportsLatest: YTS, 1337x, TPB, Nyaa.
- Query search fans out to all eight providers.
- Results are de-duplicated by torrent hash, then by id.
- ALL results are capped at 60.
- ALL search has no page 2; page > 1 returns empty.

### 3.2 Catalog findings

**H1 — Pagination can be permanently stuck (High).**  
MagnetCatalogViewModel.kt:174 sets isLoadingMore = true. loadFirstPage resets many fields at :258-270 and :287-300 but never clears isLoadingMore. loadNextPage rejects every call while isLoadingMore is true at :158-165. If a refresh, source change, filter change, or the No adult setting change occurs while a load-more request is in flight, the coroutine is cancelled at :243-244 and the cancellation path at :201-202 rethrows without clearing the flag. The archive footer can keep showing a spinner and never load another page.

**H2 — 1337x has a real failover bug (High).**  
X1337MagnetSource.kt:42-45 parses the listing and returns an empty page immediately if rows is empty. It does not try the next host. The package loops hosts at :38-67, but an empty successful-looking response defeats that loop.

The same file loads only rows.take(10) at :47 while it reports hasMore based on rows.size >= 20 at :57. Rows 11–20 of every page are never visited. Detail failures are swallowed at :91-93.

**H3 — Parse failure is reported as “no results” by several providers (High).**  
YtsResponseParser.kt:20-28 and :145-149 return an empty page when JSON is malformed. KickassMagnetSource.kt:33-39 returns a successful page even when every detail request fails, and :60-66 swallows those failures. NyaaParser and KnabenParser similarly return empty pages when the remote layout has drifted.

DefaultMagnetCatalogRepository.kt:38-43 only raises an error when every provider fails. If one provider returns an empty success, the aggregate looks healthy and the UI silently shows a short list. The UI has no per-source failure indicator.

**H4 — Filters can hit a dead end (High).**  
MagnetCatalogViewModel.kt:212-240 fetches at most three pages per filtered load (:180 and :283). If all three pages contain no match, the ViewModel returns an empty page, the grid enters its empty state at MagnetCatalogScreen.kt:255-335, and there is no load-more control in that state. The user must refresh or clear a filter; there is no “continue searching” path.

Language matching is based on title tokens in LanguageFilter.kt:97-129. The YTS structured language field is not parsed by YtsResponseParser.kt:46-135. Genre matching is reliable only where structured genres exist; other sources use title words or a generic “Movies”/“Torrent” genre.

**H5 — No adult is a heuristic, not a guarantee (High/Medium).**  
MagnetTitle.isAdult at MagnetCatalog.kt:75-85 uses category tokens and a title regex. The regex includes the token 18\+ with word boundaries. A title such as “18+ Amateur” does not satisfy the boundary after the plus sign, so the filter can miss it. Knaben hardcodes hideXXX in the request at KnabenMagnetSource.kt:30, and TPB drops every category that does not start with “2” at PirateBayMagnetSource.kt:84-85; turning the setting off cannot reveal adult results that were excluded at the source.

**H6 — Totals are not comparable (Medium).**  
DefaultMagnetCatalogRepository.kt:100-106 sums provider totalResults. The ViewModel displays that number for ALL only when there is no narrowing filter at MagnetCatalogViewModel.kt:291-295. Provider totals are a mix of total movie counts, page counts, and capped result counts. 1337x and Nyaa under-report. The UI label “TITLES” or “LINKS” does not describe what is being counted.

**H7 — Blocking provider calls ignore coroutine cancellation (Medium/High).**  
Each provider runs execute() on an OkHttp call in a withContext(Dispatchers.IO) block. Cancelling the ViewModel job does not cancel the underlying call. The epoch checks at MagnetCatalogViewModel.kt:182 and :285 discard stale results, but the network request continues until its OkHttp timeout. Search debounce is only 420 ms (:325), so typing quickly can create several background requests that survive cancellation. 1337x and Kickass add 10 and 8 detail pages, respectively.

**M1 — ALL is not one consistent feed.**  
ALL latest page 2 queries only YTS and 1337x (DefaultMagnetCatalogRepository.kt:31-37); TPB and Nyaa are dropped after page 1. ALL query is always one page and capped at 60 (:79-107). The UI can represent this as infinite content when it is not.

**M2 — TV focus is fragile in the quality sheet.**  
PlaybackQualitySheet.kt:98-102 waits 450 ms then requests focus with runCatching; it sets focusedQualityIndex = 0 even if the request failed. The Auto row is requested first even when autoPick is null, while the row is disabled at :283. Manual Up/Down handling at :129-137 can therefore start from an invalid index. FamilyGuideButton in MagnetCatalogComponents.kt:725-757 has a much smaller focus target than a 48 dp TV control.

**L1 — Trailer and Family Guide links fail silently.**  
MagnetCatalogScreen.kt:72-82 returns without feedback for a blank slug and swallows ActivityNotFoundException. The family URL is always /movie-reviews/ and strips every parenthesized group in commonsenseSlug at :84-103. “(500) Days of Summer” becomes days-of-summer. A title CSM has not reviewed produces a 404 page. Trailer search at :105-118 uses the raw release title, which can include group/quality tags.

**L2 — Dead/unused catalog surface.**  
MagnetSource.isAggregate and MagnetTitle.metaLine are not used in the reviewed flow; metaLine contains a mis-encoded separator. The VideoTitle filter in browseAllLatest can never hit CSV/BTDigg because those sources do not support latest.

## 4. Torrent streaming engine

### 4.1 Play flow (source-derived)

TorrentStreamEngine.play at TorrentStreamEngine.kt:170-328:

1. Cancel the previous job, increment generation, join cache maintenance and teardown, clear the previous handle.
2. Emit FetchingMetadata.
3. Resolve metadata: cache -> direct .torrent URL (4 s) -> swarm (up to 45 s).
4. Decode TorrentInfo, choose the largest supported video file, create a per-hash cache directory.
5. Add the torrent with SEQUENTIAL_DOWNLOAD and the video/default priorities.
6. Await the handle by polling manager.find up to 10 s.
7. Set sequential range, resume, add public trackers, boost head and tail pieces.
8. Build the video and subtitle TorrentFileStream objects.
9. Emit Buffering with the TorrentPlayback.
10. Await the opening buffer and container metadata.
11. Emit Ready.

PlayerScreen attaches Media3 as soon as Buffering contains a playback object at PlayerScreen.kt:185-189. The playback key is the absolute file path at :191, so it remains stable across Buffering -> Ready.

### 4.2 Streaming findings

**H1 — Blocked DataSource reads cannot be cancelled by stop().**  
TorrentDataSource.awaitPiece at TorrentDataSource.kt:193-207 waits for havePiece, with a 120 s video / 15 s sidecar deadline. The only early exit is closed, set by close() at :171-184. TorrentStreamEngine.stop at TorrentStreamEngine.kt:534-553 removes the torrent handle and nulls its fields, but there is no reference to the DataSource or PieceWaiter and no close/open signal. The ExoPlayer loader thread can remain blocked for up to two minutes with a RandomAccessFile open. The “Torrent playback was stopped” branch at TorrentDataSource.kt:206 is effectively unreachable because close() is driven by the same loader thread.

**H2 — Failure does not stop downloading.**  
The catch paths at TorrentStreamEngine.kt:296-326 only call setStreamingActive(false). They do not pause or remove the handle. The selected file is SEQUENTIAL and the head/tail priorities remain, so a buffer timeout, stall, or moov failure can leave the engine pulling the entire file to disk while the UI displays an error. The active cache directory is excluded from eviction at :657.

**H3 — Handle installation races a stop.**  
activeHandle = handle occurs at :254, followed by ensureCurrent at :255. If stop() runs between those lines, stop sees no activeHandle and removes nothing; the coroutine then publishes a live handle after state is Idle. No catch path clears it. The same fields are read from the main thread and the libtorrent alert thread without volatile/synchronization.

**H4 — The 8 s container window conflicts with the 120 s piece window.**  
awaitContainerMetadata uses CONTAINER_METADATA_TIMEOUT_MILLIS = 8,000 at TorrentStreamEngine.kt:1104. The DataSource allows 120 s for a video piece. Tail boost covers only the last 12 pieces at :1036-1042, while the 8 MB tail may span 32 pieces at 256 KB each. A recoverable tail can be rejected after 8 s. Head moov has no size cap either.

**H5 — Swarm metadata is not verified against the requested info hash.**  
resolveMetadata at TorrentStreamEngine.kt:427-440 checks isValidMetadata for direct and cached metadata, but for the swarm path it only uses the result to decide whether to write cache. It returns fetched regardless. play then bdecodes it at :185-199. A valid but different torrent can be played. Base32 magnets also fail the hex comparison at :469-474, causing repeated fetches.

**H6 — The cache can grow far beyond a quick-start buffer.**  
cacheLimitBytes at TorrentStreamEngine.kt:670-671 computes free/4, clamped to MIN 1 GB and MAX 16 GB. Cache maintenance at :147-151 and eviction at :650-667 only run at operations/startup. The active directory is excluded. A large stream can therefore consume a multi-GB cache until the next eviction.

**M1 — Priorities are never demoted; seek priority is stale.**  
prioritizeRange at TorrentDataSource.kt:215-232 assigns TOP_PRIORITY and a 1 s deadline but never resets them. boostInitialWindow is re-run every 500 ms at TorrentStreamEngine.kt:895 and every 200 ms in metadata waits. setSequentialRange is set once for the whole file at :260 and is not updated on seek. After several seeks, multiple 32 MB windows remain TOP_PRIORITY and compete with the current position.

**M2 — Session reuse can retain the wrong handle.**  
SessionManager.remove is asynchronous. The engine retries a play after a quick stop/retry. If the same info hash is still present, libtorrent4j can return the existing handle with its old save path/flags instead of applying the new download parameters. The app then waits for a file under the new cache directory while the native handle writes elsewhere. This is a library-behavior risk; the app does not guard with a completion wait or a manager.find-before-download check.

**M3 — Resume-data bookkeeping is a single global slot.**  
pendingResumeSave at TorrentStreamEngine.kt:162, 619 is overwritten by concurrent saves: cancellation persistCache, 60 s checkpoints, and stop. A superseded play can associate a fastresume with the wrong cache directory. SaveResumeDataFailedAlert at :726 does not verify the info hash before completing the pending request.

**M4 — Sidecar startup can block first frame.**  
TorrentDataSource.open waits for the file to exist at :111-113, with FILE_WAIT_TIMEOUT_MILLIS 30 s at :246. Sidecars <= 8 MB get a 15 s wait at :98-102. Prioritization happens only after the wait at :129-134. A subtitle source can therefore hold the merge pipeline before pieces are requested; the loader treats the resulting failure as end-of-stream.

**L1 — Parser limitations.**  
Mp4MetadataInspector.kt:52-84 treats a size-0 moov as ending at the head window rather than at file end. findMoovInTail at :86-112 scans every byte for “moov” without ftyp/mdat validation, so a byte pattern inside mdat can be a false positive. The inspector runs twice per play and allocates 2 MB + 8 MB windows.

## 5. Player and playback UI

**H1 — Background cleanup can produce a permanent dead end.**  
TorrentStreamEngine.onBackgrounded at :555-561 schedules stop after 60 s. activeJob is never set to null when a play completes, so the guard remains true after the first play, including after Ready or Failed. stop sets Idle. PlayerScreen sees playbackKey become null, stops and clears the player at :339-348. PlayerControls displays the Idle branch at PlayerControls.kt:687-690 with only Cancel. onForegrounded at :563-566 only cancels the timer; it never restarts play. This is a reproducible dead screen after backgrounding for more than 60 s.

**H2 — No first-frame watchdog.**  
onRenderedFirstFrame sets hasRenderedFrame at PlayerScreen.kt:318-320. The overlay condition at :633-643 depends on hasRenderedFrame and playerError. If the player never reports a frame and never reports an error, the overlay remains indefinitely. The engine’s metadata failure catches some cases, but a blocked DataSource, a late moov problem, or an unexpected decoder stall has no timeout.

**H3 — Retry does not retry the engine and loses position.**  
PlayerErrorOverlay’s retry at PlayerScreen.kt:645-653 only clears the error and bumps reloadKey. It does not call retryTorrent, unlike the preparation overlay at :641. pendingResumeMs is remember(playbackKey, reloadKey) initialized from the screen’s original resumePositionMs at :193-195; a reload resets to that initial position, not the current position.

**H4 — Settings are snapshotted, not observed.**  
PlayerViewModel.kt:41-49 reads hardwareDecoding and showStreamStats once. PlayerScreen.kt:197 remembers the renderers factory from that value, and :167 initializes showStats from it. Changing either setting does not update an open player.

**M1 — Quality selection intercepts Play.**  
MagnetCatalogScreen.kt:352-363 always opens PlaybackQualitySheet for both Play and Download, even when a title has one release. OnSelect at :430-444 then navigates or enqueues. A tap on Play therefore does not start the player directly; this is a UX cost and can look like the player is not starting.

**M2 — Error categories are mislabeled.**  
PlayerControls.kt:638-640 labels every TorrentState.Failed as “The swarm went quiet”, even for an unreadable container, unsupported format, or local write failure. The overlay should distinguish swarm failure from file/container failure.

**M3 — Main-thread work and recomposition churn.**  
PlayerScreen.kt:403-427 calls handle.status() every 500 ms on the main thread when stats are visible. The engine emits Buffering every 200–500 ms, causing PlayerViewModel to copy a new PlayerUiState through the whole screen. Position/state are written four times per second at :386-401. Gesture brightness writes WindowManager attributes per pointer move at :461-467 and PlayerControls.kt:1283-1287.

**L1 — Double-tap seek also toggles controls.**  
The single-tap branch in PlayerControls.kt:1327-1332 runs before the double-tap is classified, so a double-tap changes chrome visibility as well as seeking.

**L2 — Dead fatalError path.**  
PlayerUiState.fatalError is never assigned in PlayerViewModel.kt:19-31. PlayerControls has a full fatalError branch at :633-637 that cannot be reached.

## 6. Download manager, storage, and lifecycle

### 6.1 Queue lifecycle

The download queue is a whole-list Gson snapshot in SharedPreferences (DownloadStore.kt:8-28). It is saved on every mutation and unconditionally every 3 seconds (TorrentDownloadManager.kt:366-370, 576-578). The manager uses one lazy libtorrent Session at :496-519.

State path: QUEUED -> FETCHING -> DOWNLOADING -> COMPLETED/FAILED, with PAUSED as an overlay. Enqueue is asynchronous: it returns an id at :152-158 before the item exists.

### 6.2 Download findings

**C1 — Pause/remove during startup leaks an untracked torrent.**  
Between manager.download at :286 and session.handle = handle at :288 there is no suspension point. pauseLocked at :188-191 clears only session.handle and drops the active entry if the handle is null; removeLocked at :232-245 deletes both roots. A concurrent pause/remove therefore deletes the directory, then the job installs a handle. The torrent keeps writing with no active map entry. Resume calls manager.download again for the same info hash without a manager.find guard at :286, which can create a duplicate or fail. Line 261 aborts only on PAUSED, not on a removed item.

**H2 — Resume during FETCHING can start a second job.**  
Pause removes the active entry at :191 while the first job is blocked in fetchMagnet at :267-271. Resume sees no handle and calls startLocked at :219-225 without cancelling/joining the old job. Two jobs can reach :286. The identity check at :298 skips the loser’s cleanup.

**H3 — Persistence has a lost-update/resurrection race.**  
persist at :576-578 reads _downloads.value outside commandMutex. tick persists every 3 seconds at :366-370. Interleaving: tick snapshots V1 (contains X), remove saves V2 without X at :243-244, tick saves V1. X reappears on next launch as PAUSED with no file. The same unconditional write can overwrite a failed/empty load.

**H4 — A broken queue can be destroyed or crash startup.**  
DownloadStore.load at :14-20 returns emptyList on any Gson/value error. The 3-second tick then writes the empty list. Gson can also produce a null status enum or null id/magnetUrl; init at :76 dereferences item.status, causing a permanent startup crash loop. There is no schema version or last-known-good copy.

**H5 — Monitor loop has no protection.**  
monitorLoop at :318-323 has no try/catch. handle.status() is guarded at :331, but totalWanted(), downloadRate(), and numPeers() are raw JNI calls at :333-335 and :359-360 on a handle that remove may have invalidated. A native throw escapes the only monitor coroutine; SupervisorJob does not restart it. The queue can freeze or the process can crash.

**H6 — No failure detection after a download starts.**  
Tick only handles FINISHED/SEEDING at :337-344. No AlertListener is registered and status.errc()/alerts are never read. A disk-full or torrent error remains DOWNLOADING forever. FAILED is reachable only from the start path at :302-310.

**H7 — Orphan recovery marks partial downloads as COMPLETED.**  
recoverOrphanedFiles at :89-121 scans both roots, adopts any directory containing a non-empty video, and writes status = COMPLETED. It performs no piece verification. An interrupted download can therefore show “Ready” and be offered for Open folder. Recovered items use magnetUrl = “” at :107; DownloadStore.load rejects blank magnets at :16, so they disappear on every restart and are re-adopted with a new addedAt timestamp.

**H8 — No session teardown and no download fastresume.**  
The download SessionManager is never stopped and no saveResumeData is called for download handles (only TorrentStreamEngine has that logic at :534-553, :614). Every process restart re-adds and re-hashes active downloads. No close()/shutdown exists in TorrentDownloadManager or AppContainer.

**H9 — No foreground execution.**  
Downloads run in an app-scoped SupervisorJob at TorrentDownloadManager.kt:50 and start at :259. The manifest has no service at AndroidManifest.xml:47-60. WAKE_LOCK is declared at :6 but no PowerManager is used. Downloads therefore depend on the process staying alive and the screen/OS allowing it.

**H10 — Multi-file export fails.**  
savedPath is File(saveDir, info.name()) at :283. For a multi-file torrent info.name() is the root directory; for a single-file torrent it is the file. exportInternal at :425-427 checks only exists(), then publishToPublicDownloads calls source.inputStream() at :475-477. A directory throws; season packs and multi-file releases cannot be published through Save to phone. The same path is used for open-folder.

**M1 — Export/remove race.**  
exportInternal is outside commandMutex at :415-417 and removeLocked is not blocked by the exporting set at :53 and :422. If remove runs after MediaStore insert but before the current(id)==null check at :440-445, the queue item is gone and the MediaStore row survives. If remove deletes the source while copyTo is reading at :447, the export fails.

**M2 — Remote torrent names flow into local copy/delete paths.**  
savedPath from info.name() at :283 is used as a copy source at :425-426 and as an open-folder key at DownloadsScreen.kt:141-144. There is no canonical containment check in the download manager. TorrentStreamEngine does perform one at :381-383 for the streamed file; the download path does not. A name containing .. is not defended.

**M3 — Permission model is broken for API 26–28.**  
minSdk is 26 at app/build.gradle.kts:33-34. exportInternal rejects SDK < Q at :431-436. Direct storage below R requires WRITE_EXTERNAL_STORAGE at :127-131, declared maxSdkVersion=29 at Manifest.xml:8-10, but there is no requestPermissions or ActivityResultContracts call anywhere in app/src/main. The only in-app enable affordance is DownloadsScreen.kt:121-131, whose action is empty below R. Result: on API 26–28 files remain private and Save to phone always fails silently.

**M4 — MANAGE_EXTERNAL_STORAGE is over-broad and policy-sensitive.**  
Manifest.xml:7 declares MANAGE_EXTERNAL_STORAGE unconditionally. It is the only route to direct public storage, and file_paths.xml:3 exposes the entire Download/Streamline subtree. This is a restricted Play permission and a large privilege increase for an app that consumes untrusted torrent metadata.

**M5 — Root selection can change mid-item.**  
downloadRoot at :134-138 chooses public vs private at each start. If All-files access is granted or revoked between start and resume, libtorrent checks a new directory and restarts from 0%. The old partial tree is not migrated or deleted. Disk usage can double.

**M6 — FileProvider is misused as a delete handle.**  
publicUri can be a FileProvider URI (from fileProviderUri at :144-150) or a MediaStore URI. removeLocked calls contentResolver.delete on it at :236-239. FileProvider does not implement delete; the call throws and is swallowed. Actual deletion only works through the path-based deleteRecursively at :241-242. FileProvider is otherwise never used in a shared Intent.

**M7 — Open folder is fragile and hardcoded.**  
DownloadsScreen.kt:163-171 builds a DocumentsContract URI with authority com.android.externalstorage.documents and volume primary:. It does not check resolution and swallows failures at :145-147. For MediaStore-exported items savedPath is the deleted private path, so the user gets the parent folder, not the item’s folder. Secondary users/volumes are not handled.

**M8 — Storage accounting is inaccurate.**  
DownloadsHeader at DownloadsScreen.kt:353-355 sums completed totalBytes as “on disk”. After export the private copy is deleted at :447, but the same total is still displayed. There is no StatFs/free-space check anywhere before starting a download.

**M9 — Throttle updates can reorder.**

**M10 — Settings cache-clear coroutine has no finally.**

## 7. Security and privacy

**S1 — All-files access is a very large privilege.**  
MANAGE_EXTERNAL_STORAGE at Manifest.xml:7, combined with direct writes under Download/Streamline and torrent names from untrusted metadata. The app correctly canonicalizes the streamed file at TorrentStreamEngine.kt:381-383, but the download path does not. A restricted permission should be paired with strict canonical containment for every path used in copy/delete.

**S2 — Untrusted response bodies are unbounded.**  
Every provider reads response.body?.string() without a size limit: YtsMagnetSource.kt:68, PirateBayMagnetSource.kt:42, TorrentsCsvMagnetSource.kt:39, BtdigMagnetSource.kt:37, KnabenMagnetSource.kt:40, X1337MagnetSource.kt:136, KickassMagnetSource.kt:102, NyaaMagnetSource.kt:40. TorrentStreamEngine.downloadTorrentFile checks contentLength at :505-508 but calls body.bytes() at :509 and checks the actual size only afterwards. Chunked responses or missing contentLength can cause a large allocation before rejection. OkHttp callTimeout is absent for the engine client at :135-139; the direct path is wrapped in a 4 s timeout at :416-419, but the non-magnet source path at :428 is not.

**S3 — Swarm metadata is not bound to the requested hash.**  
resolveMetadata at :427-440 validates direct/cache but not the swarm result before returning. A malicious or mismatched metadata response can redirect playback to a different torrent. The direct/cache path does check at :420 and :454.

**S4 — Raw remote magnets bypass MagnetLinks validation.**  
BtdigMagnetSource.kt:83-87, KnabenMagnetSource.kt:84-86, KickassMagnetSource.kt:153-157, NyaaMagnetSource.kt:79, and X1337MagnetSource.kt:101-105 accept a magnet from HTML or an info hash fallback without a common validator. TorrentStreamEngine appends 42 public trackers at TrackerLists.kt:68-78 and announces to all at :702-704. Playing such a link discloses the device IP/info hash to arbitrary tracker hosts.

**S5 — Torrent URLs can be HTTP in Nyaa.**  
NyaaMagnetSource.kt:98 accepts http:// or https:// .torrent URLs. TorrentStreamEngine.downloadTorrentFile rejects non-HTTPS at :477-479, so the download simply fails; the UI does not explain why. The network security config blocks cleartext at network_security_config.xml:4.

**S6 — Permissions are declared but unused or unrequested.**  
WAKE_LOCK at Manifest.xml:6 is never acquired. READ_EXTERNAL_STORAGE at :11-13 and WRITE_EXTERNAL_STORAGE at :8-10 are never requested. The unused declarations increase the permission surface without enabling behavior.

**S7 — Local data is plaintext.**  
DownloadStore stores titles, magnets, paths and MediaStore URIs as plaintext JSON in SharedPreferences at DownloadStore.kt:8-28; PlaybackPositionStore stores info hashes and positions at PlaybackPositionStore.kt:58-73. Backup is disabled (allowBackup=false at Manifest.xml:18; backup_rules.xml:3-5), which limits exposure. The queue can contain adult titles; app-private storage is the only protection.

**S8 — FileProvider is not exported, but paths are broad.**  
Manifest.xml:37-45 sets exported=false and grantUriPermissions=true. file_paths.xml:3-4 exposes the whole public Download/Streamline tree and private downloads. No URI is currently shared, so the immediate exposure is limited, but the configured roots are broader than necessary.

**S9 — External links leak queries.**  
Trailer opens YouTube search with the full release title at MagnetCatalogScreen.kt:105-118; Family Guide opens a CSM URL. This is expected user-initiated behavior, but the app does not disclose it. CSM slugs can 404.

## 8. Performance, startup, and resource use

- **Two libtorrent sessions.** TorrentStreamEngine creates Session A at :686-731; TorrentDownloadManager creates Session B at :496-527. Both can run simultaneously. Neither has a close path. The app also creates a second OkHttp client for the unused ArtworkAccentLoader at AppContainer.kt:68.
- **Startup work on the main thread.** StreamlineApplication.onCreate at :17 constructs AppContainer; AppContainer.kt:76 creates TorrentDownloadManager. Its init at :72-86 performs SharedPreferences Gson load, listFiles on two roots, recursive walkTopDown, and FileProvider URI creation per recovered item. This happens before the first Compose frame. A large Download/Streamline tree can ANR.
- **Session warm-up.** TorrentStreamEngine.warmUp at :334-336 starts the native session asynchronously at app startup. It improves first-play latency but adds native initialization cost to every app launch.
- **Catalog fan-out.** ALL search launches all eight providers with no per-provider timeout at DefaultMagnetCatalogRepository.kt:84-86. The shared OkHttp client has callTimeout 30 s at AppContainer.kt:40-52; 1337x and Kickass add detail requests. Search debounce is 420 ms; typing can leave multiple blocking requests alive.
- **Streaming read-ahead.** TorrentDataSource uses 32 MB or 4–64 pieces at :89-91 and :248-250. Reads block per piece. At 4K remux bitrates, 32 MB can be under five seconds of media, so the loader can be starved even when the network is fast.
- **Player buffer.** PlayerScreen.kt:772-775 uses 5 s minimum, 120 s maximum, 1 s playback start, 3 s after rebuffer. The engine’s opening target is 1–6 MB at TorrentStreamEngine.kt:1109-1111; the two thresholds are independent. The first-frame path is not bounded by either.
- **Cache.** The stream cache retains up to 16 GB at TorrentStreamEngine.kt:1124-1126 and is evicted only at startup/play. The download manager has no free-space check.
- **UI cost.** The player emits Buffering every 200–500 ms; the ViewModel copies a new state; AndroidView updates. Stats polling is on the main thread at PlayerScreen.kt:403-427. Large grids and many card buttons add focus/layout work.
- **Storage volume.** Public direct downloads and private fallback copies can duplicate a complete file. MediaStore export copies before deleting the private source; a failure can leave both.

## 10. Prioritized remediation plan

### P0 — data integrity and user-visible correctness

1. **Serialize download lifecycle by item identity.**  
   Introduce a per-id state machine/mutex; check active[id] === session and current(id) != null before/after every transition; remove handles in a finally block; do not delete a directory while a handle is being installed; guard downloadRoot transitions.
2. **Make queue persistence transactional.**  
   Persist inside commandMutex; remove the unconditional 3 s rewrite; keep a last-known-good copy and a schema version; never overwrite an unreadable queue; handle enum/null fields defensively.
3. **Validate every remote-derived path.**  
   Canonicalize id, savedPath and info.name against the selected root before any copy/delete; reject blank/duplicate ids; do not adopt arbitrary public directories as completed downloads without verification.
4. **Handle multi-file downloads explicitly.**  
   Resolve the selected video file, not the torrent root directory, for savedPath/export; expose a file list if needed; make Save to phone open a file or a verified folder.
5. **Fix API 26–28 storage.**  
   Either request WRITE_EXTERNAL_STORAGE at the right time or remove the false enable action and present private files through FileProvider/open-with. Do not ship a button that always fails.
6. **Add a foreground execution contract.**  
   Use a data-sync foreground service (with the required notification permission) or WorkManager; persist fastresume; stop/close the native session on process lifecycle. Do not rely on an app-scoped coroutine.
7. **Bound network inputs and verify metadata.**  
   Cap response body sizes before reading; add per-provider timeouts; validate swarm metadata against the requested info hash; reject mismatched metadata.
8. **Add a first-frame/engine watchdog.**  
   If Ready/Buffering has no rendered frame for a bounded period, show a specific error and stop/pause the engine; distinguish container/file failure from swarm failure.
9. **Move recovery off the main thread.**  
   Load/recover in a background initializer and publish a ready state; avoid walking large trees in Application.onCreate.

### P1 — reliability and UX

10. Reset isLoadingMore on every new load/cancellation; make pagination visible in empty filtered states.
11. Make provider calls cancellation-aware (cancel OkHttp Call) and add per-provider timeouts; fix 1337x empty-parse failover and load all 20 rows or report the gap.
12. Add structured partial-failure reporting; do not silently drop failed sources.
13. Make filters backfill more pages or present a “continue searching” action; use structured language/genre where available.
14. Fix the No adult heuristic and source-level exclusions; add tests for 18\+, category policy, and setting churn.
15. Skip the quality sheet when only one release exists (or remember an Auto default); do not intercept every Play.
16. Add a CSM search fallback if the direct slug 404s; do not strip title parentheses that are part of the title; report external-intent failures.
17. Preserve/restore the player across background cleanup; restart or clearly return to a valid state after >60 s.
18. Make settings live (observe hardware/stats) or communicate that they apply next session.
19. Add error feedback for Save to phone, Open folder, trailer and Family Guide.
20. Harden open-folder against secondary users/volumes and no DocumentsUI handler.

### P2 — performance, quality, and tests

21. Demote stale piece priorities and update sequential range on seek; reduce TOP_PRIORITY churn.
22. Add a user-configurable cache cap and remove active-cache exemption or bound it.
23. Move stats polling off the main thread; throttle Buffering emissions.
24. Add integration tests for the engine, DataSource, download manager and player lifecycle; add instrumentation/TV tests.
25. Remove dead code/dependencies, stale ProGuard rules, unused permissions, and fix the unused metaLine encoding.
26. Add a release checklist for MANAGE_EXTERNAL_STORAGE/Play policy and signing reproducibility.

## 11. Final assessment

The app’s core design is understandable and the happy path works, but the implementation is carrying too many responsibilities in two large native-session managers and a monolithic player. The most urgent work is not adding features; it is making download state transitions and file ownership deterministic, bounding untrusted inputs, and giving Android a legitimate lifecycle for long-running transfers.

The catalog layer is broad but brittle: provider failures are often indistinguishable from empty results, filtering is heuristic, and pagination has a reproducible stuck state. The playback layer has made real progress on early source attachment and piece alerts, but cancellation, first-frame failure, and cache growth remain unresolved. The download/storage layer is the highest risk: it can lose or resurrect queue entries, leave untracked native downloads, mark partial files complete, and delete/copy paths derived from remote metadata.

All findings above are based on the current source, not on code comments or documentation.
